# Opus 4.8 튜닝 가이드

출처: platform.claude.com 프롬프트 엔지니어링(Opus 4.8 / 공통 원칙). 아래는 튜닝 시 적용할 규칙.

## 핵심 성향
Opus 4.8은 지시를 **문자 그대로, 정밀하게** 따른다. 모호하면 알아서 채우지 않는다.

## 튜닝 규칙
1. **출력을 명시.** 형식·순서·길이·톤을 적는다. "가능한 한 많은 기능을 포함해, 기본을 넘어 완성도 있게"처럼 원하면 명시적으로 요구한다.
2. **제안 vs 실행 구분.** "변경을 제안해줘"라고 쓰면 제안만 하고 안 고칠 수 있다. 실제 수정을 원하면 "구현/수정해줘"로 명확히.
3. **길이 상한.** 입력이 길면 답도 길어지니 "핵심 N개, 각 항목 ○단어 이내" 식으로 캡한다.
4. **부정형 → 긍정형.** "마크다운 쓰지 마" 대신 "매끄럽게 이어지는 산문 단락으로 작성".
5. **도구 사용은 명시하되 과하지 않게.** 필요한 도구는 "언제·왜" 쓸지 적는다. 단, 예전식 "CRITICAL: 반드시 이 도구를 써라"는 이제 **과잉 트리거**를 부르니 "~할 때 이 도구를 사용" 정도의 평범한 어조로.
6. **도구 후 요약이 필요하면 요구.** 4.8은 도구 호출 뒤 요약을 생략하고 다음 행동으로 넘어갈 수 있다.
7. **과잉설계 억제.** "요청했거나 명백히 필요한 것만. 불필요한 추상화·파일·방어코드·주석 추가 금지"를 붙인다.
8. **서브에이전트 과용 주의.** 병렬·독립 컨텍스트·독립 워크스트림일 때만 위임하고, 단일 파일 수정이나 순차 작업은 직접 하라고 지정.
9. **코딩 환각 억제.** "열어보지 않은 코드에 대해 단정하지 말고, 참조된 파일은 먼저 읽고 답하라".
10. **프론트엔드 AI slop 회피.** 진부한 폰트(Inter/Roboto/Arial)·보라 그라디언트·판박이 레이아웃을 피하고 맥락에 맞는 고유 폰트·색·마이크로 인터랙션을 요구.
