# Opus 5 튜닝 가이드

출처: platform.claude.com "Prompting Claude Opus 5". 아래는 튜닝 시 적용할 규칙.

## 핵심 성향
복잡한 에이전틱 코딩·엔터프라이즈·장기(long-horizon) 작업을 겨냥한다. 기존 Opus 4.8 프롬프트로도 잘 동작한다.
스텁·플레이스홀더 없이 작업을 끝까지 완료하며, **전체 스펙을 미리 주고 맡겨두는 방식**에서 최고 성능을 낸다.
스스로 검증·자기수정을 잘 하고, 서브에이전트 위임도 이전보다 적극적이다 — 그래서 튜닝의 상당수는 "덧붙이기"가 아니라 **"걷어내기"**다.

## 튜닝 규칙
1. **응답 길이는 프롬프트로 캡.** 기본 응답이 이전 Opus보다 길다. effort는 thinking 양을 제어할 뿐 응답 길이를 확실히 줄여주지 않으므로, 간결함은 명시한다: "핵심 답변에 집중, 면책·부연은 짧게, 설명 요청 시에만 상세히". 긴 시스템 프롬프트에서는 끝부분에 짧은 리마인더(`<tone_preference>간결하게</tone_preference>`류)를 병행.
2. **진행 나레이션의 리듬을 기술.** 에이전트 작업 중 "지금 뭘 할지"를 자주 알린다. 원하는 형태를 명시: "첫 도구 호출 전 한 문장, 이후엔 중요한 발견·방향 전환 때만 짧게, 끝나면 결과부터 먼저". 늘리거나 스타일을 바꿀 때도 같은 레버 — 부정 지시보다 **원하는 스타일의 긍정 예시**가 효과적.
3. **파일 산출물 길이 조절.** 디스크에 쓰는 보고서·문서가 이전 모델보다 길어진다. "작업에 필요한 만큼만 — 채우기용 섹션·중복 요약·보일러플레이트 금지"를 붙인다.
4. **검증 지시를 걷어낸다.** 스스로 검증한다. "최종 검증 단계를 포함하라", "서브에이전트로 검증하라" 같은 지시는 **과잉검증**을 유발하니 제거한다(레거시 harness의 별도 검증 스캐폴딩 포함). 제거해도 품질 손실 없이 토큰만 줄어든다.
5. **재확인 지시도 걷어낸다.** "double-check", "답하기 전에 재검토" 류는 모델의 자체 자기수정과 겹쳐 비용만 늘린다. 정정 나레이션이 과하면: "사용자의 코드·결론·결정이 바뀔 오류만 정정을 언급하고, 아무것도 안 바뀌는 실수는 고치고 조용히 넘어가라".
6. **범위를 고정.** 요청 밖 단계를 덧붙이거나 작업을 스스로 재해석해 확장할 수 있다. 좁은 작업엔: "요청된 범위 그대로 수행. 판단이 갈리면 확인하고, 더 나은 접근이 보이면 한 문장으로 말한 뒤 요청대로 진행. 명백히 범위 밖인 행동은 하지 않는다".
7. **서브에이전트 스폰 억제.** 위임을 이전보다 적극적으로 한다. "진짜 독립적·대형 병렬 작업만 위임. 도구 호출 몇 번으로 끝날 일은 직접. 자기 작업 검증용 서브에이전트 금지. 하나로 되면 하나만" 같은 명시적 기준 또는 결정적 스폰 캡을 준다.
8. **코드리뷰 harness.** "high-severity만/보수적으로"를 문자 그대로 따라 덜 보고할 수 있다. 발견 단계에선 "전부 보고, 필터링은 별도 단계"로 지시. 정확도가 낮은 effort에서도 유지되므로 빠른 1차 패스 + 정밀 2차 패스 구성이 가능.
9. **비전 작업엔 도구를 쥐여준다.** 차트·문서·UI 복제에 강하고, 반복 분석·크롭·시각 검증용 도구를 주는 것이 thinking을 늘리는 것보다 비용 효율적이다. 이전 모델용 vision 우회 프롬프트는 재검증(불필요해졌을 수 있음).
10. **문서·스프레드시트 작업엔 스타일 명시.** 복잡한 다중시트 스프레드시트·슬라이드를 잘 만들며, 따라야 할 스타일·템플릿이 있으면 프롬프트에 지정한다.

## 하지 말 것
- **검증·재확인 지시 추가 금지** (규칙 4·5 — 과잉검증으로 비용만 증가).
- **thinking을 끈 통합에서 "생각하지 마/추론하지 마" 규칙 금지** — 내부 태그 누출이 오히려 는다. thinking 태그를 이름으로 지목하는 지시도 비효과적이니, 일반형("내부·시스템 XML 태그를 응답에 넣지 않는다")으로 쓴다.

## 설정 레이어 (프롬프트 본문 아님 → ※ 메모로만)
- **thinking 기본 on.** 끄는 것은 effort `high` 이하에서만 가능. 대부분의 작업에서 "thinking on + low effort"가 비슷한 비용의 "thinking off"보다 낫다 — 비용 절감은 thinking off가 아니라 **effort 낮추기**로.
- **low/medium effort 품질이 강력** → 토큰·지연의 1차 제어로 적극 사용, 최난도 코딩·에이전트만 xhigh. 이전 모델에서 effort 기본값을 이관했다면 자체 평가로 스윕 재실행.
- 컨텍스트 윈도우 **1M 토큰이 기본이자 최대**이며, 창 전체에서 지시 이행·도구 호출·추론이 일관 유지.
- thinking off 시 부작용: 도구 호출이 텍스트로 새거나(`tool_use` 블록 미발행) 내부 XML 태그가 출력에 누출될 수 있음. 꼭 꺼야 하면 완화 문구: "도구 사용 전 짧은 한 문장은 말해도 된다. 맞는 도구가 없으면 추측하지 말고 그렇다고 말하라. 내부·시스템 XML 태그를 응답에 넣지 마라".
